# 프로세스에서 놓친 조건과 상태 관리 복습

날짜: 2026-10-10 Asia/Seoul

이번에 가장 오래 막힌 부분은 **대기 순서를 관리하는 일과, 아직 실행하지 않은 우선순위를 조회하는 일을 연결하는 것**이었다. 마지막 코드는 `queue<pair<int, int>>`로 순서를 유지하고, `priorities[실행한 원래 인덱스] = 0`으로 비교 대상을 관리하면서 이 문제를 해결했다.

[마지막 사용자 코드](PROCESS_USER_SOLUTION.cpp)는 함수 본문과 코드 내부 주석을 보존한 것이다. 함수 바깥의 질문 양식과 장문 설명은 소스 사본에서 생략하고 아래 검토에 관련 내용을 반영했다. 현재 판정은 코드 논리 검토이며, 프로세스의 컴파일·실행 로그와 프로그래머스 채점 결과는 아직 제공되지 않았다. AC나 독립 숙달로 기록하지 않는다.

## 실제로 헷갈렸던 지점

| 대화와 코드에서 확인한 모습 | 놓쳤던 구분 | 다음에 먼저 할 일 |
|---|---|---|
| “우선순위 1이 제일 높은 거 아니야?” | 익숙한 우선순위 관례와 이 문제의 정의 | 지문의 크다·작다를 읽고 실제 비교식으로 쓴다 |
| “queue니까 뒤에서부터 pop”이라고 해석하고 `q.back()`을 후보로 사용 | 확인할 원소와 삭제되는 원소 | `[앞 A, B, C 뒤]`를 쓰고 front·push·pop의 위치를 표시한다 |
| `location`은 인덱스인데 반환값이 1 또는 5여서 혼란 | 처음의 위치 번호와 실행 순번 | 원래 인덱스는 신원, count는 실행 횟수라고 이름 붙인다 |
| `q[i]`, 이후 `for(auto& pair : q)`를 시도 | 필요한 연산과 std::queue가 제공하는 연산 | 인덱스 조회·전체 순회가 필요한지 적고 API 지원 여부를 확인한다 |
| 큐는 변하는데 원본 priorities로 어떻게 비교하는지 질문 | 입력 당시 정보와 현재 유효한 정보 | 어떤 사건에서 어느 자료구조의 값을 바꿀지 표로 적는다 |
| `q.pop()` 뒤 `q.back()`을 다시 읽어 push하거나 대상 여부를 판단 | 변경 전 후보와 변경 후 컨테이너의 원소 | 후보를 지우기 전에 필요한 정보를 사용하거나 복사해 둔다 |
| map이면 앞 원소 삭제와 우선순위 관리가 해결되는지 질문 | 컨테이너 이름과 필요한 역할 | 순서 유지, 대상 식별, 유효성 표시, 우선순위 비교를 각각 분리한다 |

첫 문장에서 같은 우선순위여도 원래 인덱스로 구별해야 한다고 판단한 것은 맞았다. 이 판단은 최종 코드의 `pair`에 반영되어 있다. 반면 초기 설명의 “back을 기준으로”는 최종 코드의 `front()`와 맞지 않으므로 설명을 다시 쓸 때 고친다.

## 문제 정의와 큐 동작

이 문제는 숫자가 클수록 높은 우선순위다. 입력 개수 N은 1~100, 우선순위는 1~9이며, `location`은 처음 배열의 0부터 시작하는 인덱스다. 반환값은 대상의 1부터 시작하는 실행 순번이다. [공식 문제](https://school.programmers.co.kr/learn/courses/30/lessons/42587)

큐의 왼쪽을 앞이라고 쓰면 다음과 같다.

```text
front → [A, B, C] ← back
push(D) → [A, B, C, D]
pop()   → [B, C, D]       // A를 제거
```

`front()`와 `back()`은 원소를 읽고, `push()`는 뒤에 추가하며, `pop()`은 앞을 제거한다. `pop()`이 제거한 값을 반환하지는 않는다. 표준 `std::queue`는 `operator[]`나 범위 for에 필요한 공개 반복자 인터페이스를 제공하지 않는다. [C++ queue 정의](https://eel.is/c++draft/queue.defn)

따라서 queue 선택 자체는 맞다. 대기 순서를 표현할 수 있다는 이유로 전체 우선순위 검색까지 queue 하나에 맡길 필요는 없다. map으로 바꾸어도 별도 큐와의 갱신이 자동으로 연결되지는 않는다.

## 마지막 풀이에서 각 정보가 맡는 역할

| 정보 | 의미 | 변하는 때 |
|---|---|---|
| `q`의 순서 | 다음에 후보로 확인할 대기 순서 | 뒤로 보낼 때 회전하고, 실행하면 제거 |
| `q` 원소의 `first` | 처음 입력에서의 인덱스 | 바뀌지 않음 |
| `q` 원소의 `second` | 그 프로세스의 우선순위 | 대기하는 동안 바뀌지 않음 |
| `priorities[k]` | k번 프로세스가 미실행이면 원래 우선순위, 실행했으면 0 | 실제 실행할 때만 0으로 변경 |
| `count` | 실제로 실행한 프로세스 수 | 실행할 때만 1 증가 |

**큐에서 pop했다는 사실만으로 실행이 끝난 것은 아니다.** 뒤로 보내는 과정에서도 pop을 한다. `priorities`를 0으로 바꾸고 count를 늘리는 사건은 실제 실행이다.

| 사건 | q | priorities | count |
|---|---|---|---|
| 더 높은 우선순위가 있어 재대기 | 앞 원소를 뒤로 이동 | 유지 | 유지 |
| 더 높은 우선순위가 없어 실행 | 앞 원소 제거 | 해당 원래 인덱스만 0 | 1 증가 |

우선순위 최솟값이 1이므로 완료 표시 0은 어떤 대기 프로세스보다도 높다고 판단되지 않는다. 그래서 vector 전체를 순회해도 이미 실행한 항목이 방해하지 않는다. 원본 입력으로만 쓰이던 vector를 현재 상태표로도 활용한 것이다.

반대로 `erase`로 vector의 원소를 지우면 뒤의 인덱스가 당겨진다. 그러면 q에 보관한 원래 인덱스와 `priorities[k]`가 다른 프로세스를 가리킬 수 있다. 현재 코드는 위치를 보존하고 값만 바꿔 이 연결을 유지한다. 우선순위에 음수를 허용하는 다른 문제에서는 0 표시가 안전한지 다시 검토해야 한다.

## 두 구조가 함께 바뀌는 예

`priorities = [1,1,9,1,1,1]`, `location = 0`을 손으로 추적한다. A~F는 원래 인덱스 0~5다. 아래는 설명용 예상 상태이며 실행 로그가 아니다.

| 처리 | 대기 큐 | priorities | count |
|---|---|---|---:|
| 시작 | A B C D E F | 1 1 9 1 1 1 | 0 |
| A를 뒤로 | B C D E F A | 1 1 9 1 1 1 | 0 |
| B를 뒤로 | C D E F A B | 1 1 9 1 1 1 | 0 |
| C 실행 | D E F A B | 1 1 0 1 1 1 | 1 |
| D 실행 | E F A B | 1 1 0 0 1 1 | 2 |
| E 실행 | F A B | 1 1 0 0 0 1 | 3 |
| F 실행 | A B | 1 1 0 0 0 0 | 4 |
| A 실행 판정 후 대상 확인 | A B | 0 1 0 0 0 0 | 5 |

마지막 사용자 코드는 대상이면 pop 전에 break하므로 마지막 행에 A가 남아 있다. 그 상태로 반복을 종료하고 5를 반환하므로 결과에는 문제가 없다. 이후 반복을 계속하는 코드로 바꾼다면 실제 제거까지 마쳐야 한다.

## 이미 고쳐진 부분과 더 설명할 부분

- 원래 인덱스와 우선순위를 묶어 동일 우선순위의 프로세스를 구별한다.
- 후보를 `front()`로 읽고, 뒤로 보낸 뒤 앞 원소를 제거한다.
- 실행할 때만 priorities를 0으로 바꾸고 count를 늘린다.
- 삭제 전에 대상의 원래 인덱스를 확인한다.

최종 코드의 `q.push({q.front()}); q.pop();`은 올바르다. 앞 원소를 뒤에 복사한 다음 기존 앞 원소를 제거하므로 대기 순서가 회전한다. 반드시 pop을 먼저 해야 한다고 고칠 필요가 없다. pop을 먼저 하는 형태를 택할 때는 후보를 미리 값으로 복사해야 한다.

전체 priorities를 훑을 때 자기 자신의 우선순위도 검사하지만, 조건이 엄격한 `<`이므로 자신이나 같은 우선순위 때문에 재대기하지 않는다. 마지막 코드는 이 조건도 맞다.

## 반복 상태와 정답 근거

각 while 반복이 시작될 때 다음 세 문장이 성립한다.

1. q에는 아직 실행하지 않은 프로세스가 정확히 한 번씩 대기 순서대로 있다.
2. priorities에는 미실행 프로세스의 우선순위가 원래 위치에 남고, 실행한 위치에는 0이 있다.
3. count는 지금까지 실행한 프로세스의 수다.

초기에는 모두 대기 중이고 count가 0이므로 성립한다. 재대기하면 순서만 회전하여 세 의미가 유지된다. 실행하면 해당 상태를 0으로 표시하고 count를 늘린 뒤 q에서 제거하여 다음 반복에서도 의미가 유지된다. 대상 발견 시에는 곧바로 종료하므로 앞 절의 세 문장을 그 중간 지점까지 항상 성립한다고 주장하지 않는다.

따라서 priorities에서 후보보다 높은 양수를 찾는 것은 아직 실행하지 않은 더 높은 우선순위가 있는지 묻는 것과 같다. 있으면 재대기, 없으면 실행이라는 지문의 규칙을 그대로 구현한다. 대상일 때 증가시킨 count가 반환할 실행 순번이다.

남은 프로세스 중 최고 우선순위는 앞에 도달하면 실행된다. 낮은 우선순위가 뒤로 이동해도 이 최고 우선순위는 유한 번의 후보 확인 뒤 앞에 도달하므로, 재대기만 무한히 반복되지 않는다. 실제 실행마다 남은 수가 줄고 유효한 location의 대상도 결국 실행된다.

## 비용을 계산할 때 놓치지 않을 점

N은 처음 입력 개수, P는 서로 다른 우선순위의 개수라고 하자. 후보 한 번을 판단할 때 priorities를 최대 N개 비교한다. pop과 push를 반복하므로 while을 단순히 N회라고 세면 안 된다.

현재 최고 우선순위를 모두 실행할 때까지 대기열을 한 바퀴 살피면 충분하다. 그 단계에서 낮은 우선순위는 뒤로 이동하고, 최고 우선순위는 실행되어 사라진다. 이런 단계가 최대 P개이므로 후보 확인은 O(PN), 각 확인의 배열 순회는 O(N)이다.

```text
전체 시간 상한: O(PN²)
이 문제는 P ≤ 9이므로: O(N²)
추가 큐 저장 공간: O(N)
```

모두 같은 우선순위이고 마지막 항목이 대상이면 후보 N개마다 배열 N칸을 끝까지 검사하므로 실제로 Θ(N²)에 도달한다. vector 값 매개변수의 복사 비용도 O(N)이며 전체 시간·공간 차수를 높이지 않는다.

이 결론은 우선순위 종류가 9개 이하라는 조건을 사용한다. 우선순위를 N개의 서로 다른 값까지 허용하면 이 방식은 최악 O(N³)이 될 수 있다. 예를 들어 1부터 N까지 오름차순인 입력에서 첫 원소를 대상으로 삼으면, 여러 번 회전하면서 뒤쪽의 큰 값을 다시 찾는다. 코드의 반복문 모양만으로 복잡도를 고정하지 않는다.

이 풀이는 유효한 직접 시뮬레이션이다. 다른 자료구조로 더 빠르게 만드는 것과, 현재 풀이가 왜 맞는지 설명하는 것은 별도의 학습 과제다.

1. **문제 규칙:** 어느 쪽이 높거나 빠르며, 같은 값은 어떻게 처리하는가?
2. **저장 의미:** 각 자료구조의 원소는 누구의 어떤 정보를 나타내는가?
3. **변경 규칙:** 한 사건 뒤에 무엇을 바꾸고 무엇을 유지하는가?
4. **검증 근거:** 이 규칙을 틀리게 구현하면 어떤 작은 입력에서 드러나는가?

먼저 답할 질문은 하나다. **“같은 프로세스를 뒤로 보낼 때와 실제 실행할 때, priorities를 각각 어떻게 처리하며 왜 그렇게 하는가?”** 코드를 가리고 이 차이를 설명한 뒤 작은 입력을 추적하면, 단순히 같은 코드를 다시 읽는 것보다 이번 혼동이 정리되었는지 확인하기 좋다.
