# 도움받아 수정한 트럭 풀이의 복원 연습

작성일: 2026-10-11 Asia/Seoul

[사용자 코드와 답변 원문](BRIDGE_TRUCK_ASSISTED_SOLUTION.cpp)은 도움받아 수정한 풀이로 보관한다. 줄 끝 공백만 정리했으며 코드와 주석, 미답 칸을 유지했다. 이 파일은 수정본의 기록이며 코딩 프로젝트의 빌드 대상으로 추가하지 않았다.

이번 공유본에는 이동 순회를 마친 뒤 퇴장 처리하는 구조, 빈 대기 큐 검사, 진입·퇴장 무게 갱신이 모두 반영됐다. 이전 결함이 남은 버전과 구별한다. 실제 C++ 빌드·실행·채점과 독립 복원은 아직 확인하지 않았다.

## 지금 연습할 순서

1. **참고 코드를 가린다.** 1~6의 초안을 자기 말로 짧게 쓴다. 특히 상태의 뜻과 진입·이동·퇴장 때 바뀌는 정보를 먼저 확인한다. 문장이 막히면 작은 입력으로 돌아간다.
2. **작은 입력을 손으로 추적한다.** `bridge_length=2`, `weight=10`, `truck_weights=[7,4]`에서 매초 다리 위 트럭, 총무게, 완료 개수를 적는다. 반환값만 맞히지 말고 변화의 이유도 적는다.
3. **추적한 절차를 빈 화면에서 구현한다.** 앞서 본 코드와 같은 변수명·컨테이너를 재현할 필요는 없다. 자료구조를 고른 이유와 실제 지원 연산이 맞는지 확인한다.
4. **예상값과 실제값을 비교한다.** 작은 입력과 공식 예제, 자신이 정한 경계 사례를 실행한다. 틀리면 최초로 달라진 상태 하나를 찾고 그 부분부터 수정한다.
5. **시간을 두고 다시 확인한다.** 오늘 복원 후 다음 날 한 번, 며칠 뒤 숫자를 바꾼 입력으로 다시 설명·구현을 시도한다. 이 간격은 실천용 제안이며 개인에게 최적인 간격을 측정한 결과가 아니다. 수행 전에는 완료로 기록하지 않는다.

막혔을 때는 필요한 개념이나 해당 부분만 확인하고 다시 가린다. 문법을 찾아봤는지, 이동·퇴장 순서나 전체 풀이를 봤는지 도움의 범위를 짧게 남긴다. 참고 없이 오래 멈춰 있는 시간을 성과로 세지 않는다.

## 이 순서를 권하는 근거

기억에서 답을 꺼내는 연습, 설명 질문, 시간을 두고 복습하기, 풀이 예시와 직접 문제 해결을 번갈아 하기에는 학습 연구에 근거한 권고가 있다. [미국 교육과학연구소 학습 가이드](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)

위 절차는 그 일반 원칙을 이번에 관찰한 상태 갱신·코드 범위 혼동에 적용한 코치의 제안이다. 이 사용자의 뇌에 가장 효율적이라고 실험한 방법이나 C++ 성적 향상을 보장하는 공식은 아니다. 정확히 암기한 줄 수보다 다른 작은 입력에서 설명·구현이 유지되는지를 확인한다.

## 도착 시각을 저장하는 표현으로 변경

사용자는 같은 코드를 복원하는 데서 더 나아가, 더 간결한 표현을 선택하는 사고를 연습하고 싶다고 밝혔다. 진입 시각 질문을 받은 뒤 진입 시각에 다리 길이를 더하면 퇴장 시각을 알 수 있고, 모든 트럭의 남은 시간을 줄일 필요가 없다고 설명했다. 전체 순회가 필요하다고 생각해서 vector를 골랐다는 자신의 선택 근거도 설명했다. queue와 pair의 역할을 코치가 연결해 설명한 뒤, 사용자는 `{무게, 퇴장 예정 시각}`을 저장하는 코드로 바꾸었다.

첫 queue 시도는 진입 시 다리 큐에만 추가하고 총무게 증가와 대기 큐 제거를 누락했다. 피드백 후 먼저 pop을 추가한 [중간 시도](BRIDGE_TRUCK_QUEUE_ATTEMPT.cpp)를 보관했다. 이후 총무게 증가도 반영한 [최신 코드와 원문 답변](BRIDGE_TRUCK_QUEUE_SOLUTION.cpp)을 보관했다. 두 파일 아래에 이전 vector 풀이 전체와 1~8 답변을 주석으로 추가했으며, 기존 원본도 유지했다.

최신 코드에서 진입은 총무게 증가 → 다리 큐 추가 → 대기 큐 제거로 일관된다. 퇴장은 총무게 감소 → 다리 큐 제거 → 완료 개수 증가로 반영된다. 표현을 바꾸어도 사건별로 갱신해야 할 상태는 유지된다는 점이 이번 확인 항목이다.

- pair의 first는 무게, second는 퇴장 예정 시각이다. 앞서 논의한 `{진입 시각, 무게}`와 필드 의미가 달라졌지만 최신 코드는 일관되게 사용한다.
- 사용자 회고의 “진입 시각과 경과 시간을 더한다”는 표현은 **진입 시각 + bridge_length = 퇴장 예정 시각**으로 정확히 표현할 수 있다. 사용자 원문은 수정하지 않았다.
- 현재 코드는 time=0에서 시작해 반복 끝에 증가하는 내부 시간 기준을 유지한다. 이 기준에서 한 트럭의 반환값은 L+1이다. 시간이 매 반복 1씩 증가하고 진입이 최대 한 대이며 모두 같은 L초 뒤 퇴장하므로 front 하나를 `== time`으로 검사할 수 있다.
- 이번 queue 구현은 질문과 설명을 받은 뒤 작성하고 누락을 수정한 결과다. 새로운 표현의 이해와 구현 수정은 확인했지만, C++ 실행·프로그래머스 AC·무힌트 복원은 확인하지 않았다.

다음 확인은 작은 입력 `L=2, weight=10, [7,4]`에서 매 반복 후 총무게가 실제 다리 위 무게 합과 같은지 추적하는 것이다. 1~8 전체를 다시 쓰기보다 5번의 표현 선택 근거와 6번의 상태 의미를 기존 답변에 보완한다. 사용자가 제시한 이후 학습 순서는 스택/큐 복습 → LostArk 기술소개서 → 시스템 프로그래밍·운영체제이며, 이후 작업은 아직 시작하지 않았다.

## 전체 답변 제출과 채점

사용자는 스택/큐 여섯 문제의 1~8을 정리한 뒤 힙 세 문제로 진행하기로 하고, 첫 번째로 트럭의 전체 답변을 제출했다. [원문](BRIDGE_TRUCK_ANSWERS.cpp)과 [항목별 채점 및 보완](BRIDGE_TRUCK_REVIEW.md)을 보관했다. 설명 점수는 6/16이며 필요한 상태와 처리 절차는 일부 설명했다. 반복 횟수와 실행 시간 단위, N과 L, 최대 저장량과 정확성 근거를 보완할 차례다. 현재 코드는 정적으로 일관되지만 새 실행·AC 증거는 없다. 위 초기 성과표는 이 답변 이전의 상태다.
