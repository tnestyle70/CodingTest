# 스택과 큐 여섯 문제의 약점과 복습 출발점

작성일: 2026-10-11 Asia/Seoul

지금 우선 연습할 것은 **저장한 상태의 의미를 정하고, 사건마다 함께 바뀌어야 하는 값과 실행 순서를 코드에 연결하는 것**이다. 프로세스의 재대기·실행, 트럭의 진입·이동·퇴장, 순회 중 삭제에서 이 연결의 혼동이 반복되었다. 이것은 관찰된 학습 과제이며 지능·적성·의지에 대한 판정이 아니다. 복기를 하지 않았기 때문이라는 인과관계도 현재 대화만으로 확정하지 않는다.

도움을 받아 수정한 풀이는 학습 경험으로 기록한다. 독립적으로 풀 수 있는지는 해설을 가린 상태에서 설명·구현·검증하는 별도의 과제로 확인한다. 답변 양식을 채웠다는 사실만으로 독립 풀이 능력을 확정하지 않는다.

## 여섯 문제에서 실제로 확인한 것

공식 스택/큐 Kit는 아래 여섯 문제다. 현재 문제 수와 채점 완료 수는 서로 다르다. [공식 목록](https://school.programmers.co.kr/learn/courses/30/parts/12081)

| 문제 | 확인한 시도와 성과 | 보완하거나 확인할 점 |
|---|---|---|
| 같은 숫자는 싫어 | 오른쪽 비교 풀이를 수정하고 정확성 17개·효율성 4개 통과, 100점 보고. 작은 경계 입력 두 개 통과 보고 | 마지막 구간의 대표 선택, 개수와 값 범위, 비용 산술, answer 전체의 의미. 기존 [답변](../10-10/SAME_NUMBER_ANSWERS.md)과 [6/16 검토](../10-10/SAME_NUMBER_REVIEW.md) 보존 |
| 올바른 괄호 | 닫는 괄호 앞에 미처리 열린 괄호가 필요함을 말하고 stack 구현을 제시. 빈 스택 검사와 마지막 잔여 검사 포함 | 큰 방향과 코드 논리는 맞음. 나머지 설명 칸과 실제 제출 결과 미확인. 자료구조 이름보다 저장 정보의 의미를 설명하는 연습 |
| 기능개발 | 매일 진척률을 올리고 앞 작업부터 묶어 배포하는 시뮬레이션 제시 | `progresses[index] >= 100 && index < progresses.size()`에서 접근이 범위 확인보다 먼저 일어남. index가 끝에 도달하는 최소 입력 추적 필요 |
| 프로세스 | 원래 인덱스와 우선순위를 묶고, 실행 시 priorities를 0으로 표시하는 일관된 최종 코드 제시 | front/back, 원래 인덱스와 실행 순번, 재대기와 실제 실행, queue API 구분. [상세 검토](../10-10/PROCESS_REVIEW.md) |
| 다리를 지나는 트럭 | 시간별 시뮬레이션 제안, 빈 대기 큐·무게 갱신·완료 개수 수정. 후속으로 이동 순회 밖에서 퇴장 처리하는 [수정본](BRIDGE_TRUCK_ASSISTED_SOLUTION.cpp) 공유 | 이전 혼동의 독립 설명과 재구현을 확인할 차례. [복원 연습](BRIDGE_TRUCK_RETRY.md) |
| 주식가격 | 참고 코드를 보관한 뒤, 각 시점에서 뒤쪽 가격을 검사하는 직접 풀이 제시. 하락 시점까지 count하는 코드 논리는 맞음 | 설명의 비교 방향과 실제 코드가 반대였음. 최악 O(N²) 비용 및 실제 효율성 채점 미확인. 별도 참고 풀이의 독립 유도는 주장하지 않음 |

이번 기록에서 AC 증거가 확인된 신규 스택/큐 문제는 같은 숫자는 싫어 한 문제다. 트럭에 대해서는 사용자가 이번 회고에서 “어제 도움받아 풀었다”고 보고했다. 초기 회고 시 마지막 코드에는 순회 중 erase가 남아 있었으나, 이후 공유한 수정본에는 이 문제가 제거됐다. 수정본과 질문·답변을 함께 보관했다. 채점 결과와 독립 복원은 아직 확인하지 않았다.

## 반복된 약점과 확인 방법

| 연습할 항목 | 대화에서 확인한 근거 | 다음에 만들 산출물 |
|---|---|---|
| 목표와 구현 절차 분리 | 여러 문제에서 1번에 반복문·자료구조·구현 계획을 길게 쓰고 2~6번은 공란으로 유지 | 목표는 입력·규칙·출력 한 문장. 구현 문장은 버리지 않고 4~6번으로 옮김 |
| 숫자와 변수의 의미 고정 | N과 원소 값 범위, location과 실행 순번, 현재 무게와 매초 누적값의 혼동 | 각 변수에 의미·단위 한 줄. 입력 범위와 복잡도 표기를 별도로 작성 |
| 사건별 상태 갱신 | 프로세스에서 완료 항목 제외 방법 질문. 트럭에서 이동 중 무게를 다시 더하거나 진입 시 필요한 덧셈까지 주석 처리 | 사건 → 바뀌는 값 → 유지되는 값 표 |
| 안전한 접근과 실행 범위 | 기능개발에서 범위 확인 전 인덱스 접근. 프로세스에서 pop 뒤 원소 확인. 트럭에서 빈 front와 순회 중 erase | 읽기 전 유효성 확인, 삭제 전후 대상 구별, 순회가 끝나는 중괄호 표시 |
| 연산 비용 합산 | N² 수치 오류, 고정 연산/초 환산, O(N)을 수치 범위처럼 표현 | 최악 입력 한 개와 작업 횟수 × 한 번 비용. 출력 포함 여부를 적은 공간 비용 |
| 오류 원인 검증 | 트럭에서 덧셈을 켜고 끄며 시간 초과·1 차이를 질문. 정확한 실패 입력·예상 상태·실제 상태가 함께 제공되지는 않음 | 가장 작은 실패 입력, 기대/실제 출력, 처음 달라지는 변수와 시점 |

숫자 해석에는 후속 개선도 있었다. 사용자는 N을 원소 개수로 바로잡았고 N²의 지수도 10¹²로 수정했다. 당시 값 범위 `0~0` 표기와 `10¹²=100억`이라는 읽기는 추가 교정이 필요했다. 이후 N의 범위를 1~1,000,000, 원소 값 범위를 0~9로 정확히 답하고 트럭으로 이동하기를 선택했다. “배열의 개수”는 “배열 안 원소 개수”, “i번째”는 “인덱스 i인 원소”로 표현을 보정했다. 3·6번의 설명은 별도 보완 대상으로 유지하며 과거 6/16을 현재 능력의 고정 점수로 사용하지 않는다.

## 다리를 지나는 트럭에서 수정이 엇갈린 이유

접근 자체는 가능한 시간별 시뮬레이션이었다. 필요한 동작을 말로 떠올렸지만 서로 다른 사건의 갱신과 코드 블록의 경계를 한 번에 유지하는 데 어려움이 드러났다.

| 항목 | 관찰된 과정 | 현재 판단 |
|---|---|---|
| 처리 순서 | 처음에는 진입 조건 판단 뒤 이동. 이후 이동을 조건문 앞으로 옮김 | 방향을 바로잡음 |
| 총무게 | 처음 진입 합산 누락. 이동 반복 안에서 합산을 검토. 이후 진입 합산도 주석 처리했다가 복구 | 마지막 게시본의 진입 증가·퇴장 감소는 맞음. 사건별 이유의 독립 설명은 확인 전 |
| 빈 큐 | 모든 대기 트럭이 올라간 뒤에도 front 접근. 이후 empty 검사를 왼쪽에 추가 | 마지막 게시본에 반영됨 |
| 삭제 위치 | 여러 수정본에서 도착 처리와 erase가 범위 for 안에 유지됨. 코치가 for를 닫은 뒤 퇴장 처리하는 부분 코드를 제공 | 후속 공유본에 수정 반영. 코드 없이 이유를 설명하고 복원하는 과제는 남음 |
| 완료 정보 | 완료 트럭 queue를 정수 complete로 변경 | 종료 판정에 필요한 개수로 정보를 줄인 유효한 변경 |

`totalBridgeWeights`는 지금 다리 위에 있는 무게의 합이다. 이 변수는 모든 방문에서 더하는 누적 점수가 아니다.

| 사건 | 다리 위 트럭 목록 | 총무게 | 완료 개수 |
|---|---|---|---|
| 진입 | 새 트럭 한 대 추가 | 진입한 무게만큼 증가 | 유지 |
| 이동 | 남은 시간 감소 | 유지 | 유지 |
| 퇴장 | 도착한 트럭 제거 | 퇴장한 무게만큼 감소 | 1 증가 |

예를 들어 다리 위에 7짜리 트럭 한 대가 계속 있다면 시간이 지나도 총무게는 7이다. 이동 때마다 7을 더하면 실제 무게와 변수가 달라져 진입을 부당하게 막을 수 있다. 무게를 증가시키는 줄 자체가 나쁜 것이 아니라 **어떤 사건에서 실행하는가**가 중요하다.

순회 중 vector의 앞 원소를 erase하면 이후 원소의 위치가 당겨지고 사용 중인 반복자가 무효화된다. 이 경우 실행 결과를 근거로 정확히 1초만 잘못 셌다고 해석할 수 없다. 이동 순회를 마친 뒤 퇴장 처리 전체를 수행하는 구조를 코치가 제시했다. [C++ vector 삭제 규칙](https://eel.is/c++draft/vector.modifiers)

같은 문제가 반복됐다는 사실은 해당 수정의 실행 위치를 아직 확인해야 한다는 근거다. 사용자가 설명을 무시했거나 이해하려 하지 않았다는 근거로 확대하지 않는다. 코치도 교체 코드를 제공한 뒤 다음 입력에서 직접 설명·추적하게 하는 확인을 더 분명하게 연결해야 한다.

## 다시 시작할 곳

**같은 숫자는 싫어를 짧은 기준 문제로 다시 잡는다. 기존 답변과 코드는 보존하고 2번 → 3번 → 6번만 우선 보완한다.** 이미 맞게 설명한 직접 풀이를 다시 공란으로 만들지 않는다. 특정 불변식 문장을 암기하는 대신 자신의 방식이 유지하는 상태를 작은 입력에 적용한다.

| 순서 | 할 일 | 다음으로 넘어갈 근거 |
|---|---|---|
| 1 | 같은 숫자는 싫어의 숫자 역할·비용·answer 의미를 보완 | 자기 말로 설명하고 작은 입력에서 그 설명이 유지되는지 확인 |
| 2 | 트럭의 진입·이동·퇴장 상태표를 코드 없이 작성 | 사건별 무게·목록·완료 개수 변화를 설명하고 두 트럭을 손추적 |
| 3 | 트럭의 이동과 퇴장을 분리해 직접 재구현 | 빈 큐 접근과 순회 중 삭제가 없는지 확인, 예상값과 실제 실행 비교 |
| 4 | 프로세스의 재대기·실행 상태표를 코드 없이 작성 | 위의 상태 갱신 원칙을 다른 문제에서도 적용 |
| 5 | 나머지 세 문제의 미답·검증을 각각 보완하고 새 문제로 진행 | 같은 설명을 복사하는 대신 문제별 상태와 비용을 직접 생성 |

여섯 문제를 전부 초기화하거나 첫 문제에서 16/16 문구를 완벽히 외울 때까지 머물지 않는다. 도움을 받은 뒤의 재구현은 복원 연습으로, 처음 보는 문제의 독립 유도와는 구분한다. 달력의 날짜가 바뀌었다는 것만으로 24시간 지연 복습을 수행했다고 기록하지 않는다.

초기 확인 과제였던 아래 두 문장의 범위는 사용자가 정확히 답했다. 현재는 사용자 선택에 따라 [트럭 복원 연습](BRIDGE_TRUCK_RETRY.md)으로 진행한다.

```text
N = arr.size()는 ______의 개수이며, 범위는 ______이다.
arr[i]는 ______이며, 값의 범위는 ______이다.
```

이전 원문은 보존한다. 이미 바로잡은 범위를 다시 오류로 취급하지 않으며, 비용과 불변식의 남은 설명은 이후 별도로 확인한다.
