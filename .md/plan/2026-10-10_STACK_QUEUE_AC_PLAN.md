# 같은 숫자는 싫어 AC 보관과 사고 과정 정리 계획

작성일: 2026-10-10 Asia/Seoul

## 요청과 증거

- 사용자가 제시한 최신 오른쪽 비교 코드를 CodingTest에서 Git으로 관리한다.
- 사용자 보고로 정확성 17개와 효율성 4개 통과, 총점 100.0을 확인했다.
- 처음 제시한 왼쪽 비교 코드는 과거 풀이를 참고한 것이며, 새로 재구성한 코드는 오른쪽 비교다.
- 첫 재풀이의 마지막 연속 구간 누락, 질문 힌트, 사용자 수정, AC를 구분하여 기록한다.
- 코드 작성은 코딩테스트 프로젝트, 중단점 검증은 Debugging 프로젝트라는 사용자의 작업 방식을 유지한다.

## 작업

1. AC 코드를 미화하거나 로직을 바꾸지 않고 problems/stack_queue에 보관한다.
2. 코딩테스트에 편집용 복사본을 두고, 별도 Debugging 파일에서 이를 포함해 공식 예제와 경계를 검증할 수 있게 한다. 이전 Debug.cpp는 보존한다.
3. 현재 풀이의 연속 구간 끝 선택과 대기 중인 구간을 반영하여 불변식을 설명한다.
4. 리뷰·세션 기록·학습자 맥락·진도표·문서 링크를 갱신한다. AC 6/47, 스택/큐 1/6으로 올리며 Reviewed/Mastered는 독립 증거 없이 올리지 않는다.
5. 기존 공통 8단계 정본에 연결된 작성 가이드와 100문항의 문서 링크·번호·중복을 확인한다.
6. 가능한 로컬 빌드·실행을 수행하고, 도구가 없으면 그 제한을 실제 실패 결과와 함께 기록한다. 사용자 Judge와 로컬 실행을 혼동하지 않는다.
7. 요청 범위의 변경을 검토해 Git으로 커밋하고 원격 main에 일반 push한다.

## 완료 기준

- 사용자 AC 원본과 편집용 코드가 일치한다.
- 새 테스트용 실행 진입점이 이전 사용자 풀이를 덮어쓰지 않는다.
- 관찰한 약점·현재 해석·미평가 능력이 구분된다.
- 제출 성공을 무힌트 독립 복원이나 숙달로 확대하지 않는다.
